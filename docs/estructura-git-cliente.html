Estructura Git de GIS_QB

Modelo propuesto para conservar el código fuente, las Experiences editables y las versiones listas para producción en un único repositorio trazable y reutilizable.

1. Objetivo

GIS_QB se propone como la fuente oficial para reconstruir, mantener y desplegar las soluciones de Hidrograma desarrolladas con ArcGIS Experience Builder Developer Edition.

El repositorio no contiene la instalación completa de Experience Builder. Conserva únicamente los componentes propios del proyecto y las entregas necesarias para que otro integrante pueda continuar el trabajo o desplegar una versión aprobada.

Resultado esperado: un nuevo desarrollador puede clonar GIS_QB, conectar los widgets a su instalación local, importar las Experiences y reproducir la solución sin depender del equipo donde fue creada.

2. Principios de la propuesta

1

Una fuente oficial

Los cambios aprobados se conservan en Git y no dependen de carpetas personales o copias manuales.

2

Artefactos separados

El código fuente, el proyecto importable y el build de producción cumplen propósitos distintos.

3

Trazabilidad

Cada entrega relaciona el cambio del widget con la Experience y la versión desplegable correspondiente.

4. Tipos de artefactos

Artefacto Ubicación Propósito Uso
Código fuente widgets/** Implementación editable de los widgets personalizados. Desarrollo, revisión y pruebas.
Paquete importable experiences/packages/*.zip Experience reutilizable generada oficialmente por Experience Builder. Importar y continuar editando en otro ambiente.
Build de producción experiences/*/app Aplicación web compilada y lista para alojar en un servidor. Pruebas finales y despliegue.
Documentación docs/** Procedimientos técnicos, arquitectura y reglas de colaboración. Incorporación, soporte y auditoría.
El paquete ZIP no debe abrirse y volver a comprimirse manualmente. Se genera con las herramientas de Experience Builder para conservar su estructura, versión y configuración de inicio de sesión.

5. Flujo de publicación

Editar el widget o la configuración
Probar y guardar la Experience
Generar paquete y build
Validar producción
Revisar, aprobar y publicar en Git

Relación entre los componentes

Una modificación funcional no se considera completa hasta actualizar los artefactos que correspondan:

  • El código fuente refleja la implementación realizada.
  • La Experience importable conserva la configuración editable.
  • El build de producción contiene el widget compilado.
  • La versión desplegada fue probada mediante HTTP.
  • El commit identifica claramente el alcance de la entrega.

6. Responsabilidades por rol

Rol Responsabilidad principal Entrega esperada
Desarrollador Implementar, revisar y probar el código del widget. widgets/**
Analista GIS Configurar la Experience, integrar widgets y validar el comportamiento funcional. packages/*.zip
Responsable de publicación Generar y probar la aplicación compilada con su configuración de autenticación. experiences/*/app
Revisor Confirmar consistencia entre fuente, Experience y producción antes de aprobar. Pull Request

7. Política propuesta de control de versiones

  • main representa la última versión estable y reproducible.
  • Los cambios se desarrollan en ramas con nombres descriptivos.
  • La revisión se realiza mediante Pull Request antes de integrar a main.
  • Los commits separan, cuando sea útil, documentación/configuración y cambios funcionales.
  • Los archivos temporales y dependencias locales permanecen fuera de Git.
El Client ID forma parte de la configuración pública del build; tokens, secretos OAuth y credenciales personales nunca deben incluirse.

8. Contenido mínimo de una entrega

Tipo de cambio Widget Paquete importable Producción
Cambio únicamente de documentación No No No
Cambio interno del widget sin impacto visual Sí Según impacto Sí, si se despliega
Cambio de interfaz o comportamiento Sí Sí Sí
Cambio de configuración de la Experience No necesariamente Sí Sí

9. Beneficios para el proyecto

Continuidad

El conocimiento y los entregables dejan de depender de un único ambiente de desarrollo.

Reproducibilidad

Otro integrante puede reconstruir la solución con los mismos widgets y Experiences.

Auditoría

Git conserva quién cambió cada componente, cuándo se modificó y con qué propósito.

La estructura propuesta permite administrar GIS_QB como un producto: código editable, proyecto reutilizable, versión desplegable y documentación evolucionan juntos bajo control de versiones.
