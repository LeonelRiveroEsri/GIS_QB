2. Requisitos

  • Windows con Git.
  • Acceso al repositorio LeonelRiveroEsri/GIS_QB.
  • ArcGIS Experience Builder Developer Edition en la misma versión usada por el equipo.
  • Node.js y npm compatibles con esa versión de Experience Builder.
  • Cuenta y Client ID del mismo portal de ArcGIS Online o Enterprise.
  • Python 3 es opcional para el futuro script de sincronización; el flujo validado en este documento usa CMD y Node.js.
Nunca guardar tokens, contraseñas, secretos OAuth ni archivos de sesión dentro de Git. El Client ID puede configurarse localmente, pero las credenciales personales no se versionan.

3. Instalación desde cero

3.1 Clonar GIS_QB

Mantener el repositorio Git separado de la instalación de Experience Builder:

D:\EXP_GIT          → Experience Builder Developer Edition
D:\EXP_GIT\GIS_QB   → repositorio Git dentro del ambiente

3.1.1 Comprobar que el destino esté libre

En una terminal CMD de VS Code:

if exist "D:\EXP_GIT\GIS_QB" (echo EXISTE) else (echo NO_EXISTE)

Para una instalación nueva, el resultado esperado es:

NO_EXISTE
Si aparece EXISTE, no volver a clonar ni eliminar la carpeta automáticamente. Primero comprobar si ya contiene un repositorio válido.

3.1.2 Clonar el repositorio

git clone https://github.com/LeonelRiveroEsri/GIS_QB.git "D:\EXP_GIT\GIS_QB"

Esperar hasta recuperar el prompt y confirmar que la descarga termine con Updating files: 100%.

3.1.3 Validar la rama y el estado

git -C "D:\EXP_GIT\GIS_QB" status -sb

El resultado esperado es:

## main...origin/main

No deben aparecer archivos modificados ni pendientes.

3.1.4 Validar el remoto

git -C "D:\EXP_GIT\GIS_QB" remote -v

Las direcciones de lectura y escritura deben corresponder al repositorio oficial:

origin  https://github.com/LeonelRiveroEsri/GIS_QB.git (fetch)
origin  https://github.com/LeonelRiveroEsri/GIS_QB.git (push)

3.1.5 Usar la configuración compartida de VS Code

El repositorio incluye .vscode/settings.json. Para que VS Code aplique esta configuración, abrir GIS_QB como carpeta raíz y no solamente un archivo o la carpeta superior D:\EXP_GIT:

code "D:\EXP_GIT\GIS_QB"

También se puede usar Archivo → Abrir carpeta y seleccionar D:\EXP_GIT\GIS_QB. Si VS Code solicita confirmar la confianza del espacio de trabajo, hacerlo únicamente después de comprobar que corresponde al repositorio oficial.

La configuración compartida establece, entre otros aspectos:

  • CMD con Node.js como terminal predeterminada.
  • Node.js desde D:\node\node-v24.
  • Formato al guardar y organización explícita de imports.
  • Prettier como formateador para TypeScript, JavaScript, JSON y CSS.
  • Exclusión de node_modules, dist y build de las búsquedas.
  • Descarga automática del estado remoto de Git mediante git.autofetch.
Las rutas de Node.js corresponden al ambiente estándar del proyecto. Si otro equipo instala Node.js en una ubicación diferente, debe acordar el cambio antes de modificar y subir .vscode/settings.json. Una preferencia estrictamente personal debe guardarse en la configuración de usuario de VS Code, no en este archivo compartido.

Para disponer del formato configurado, instalar en VS Code la extensión Prettier - Code formatter (esbenp.prettier-vscode). Después, abrir una terminal nueva y validar:

where.exe node
where.exe npm
node --version
npm --version

No copiar manualmente D:\EXP_GIT\.vscode después de clonar: la versión oficial ya viaja dentro de GIS_QB\.vscode y se actualiza mediante git pull.

3.2 Instalar Experience Builder

Descargar Experience Builder Developer Edition, descomprimir la versión acordada por el equipo en D:\EXP_GIT y validar la versión:

type "D:\EXP_GIT\version.json"

La instalación validada para GIS_QB usa exbVersion: 1.20.0.

3.2.1 Validar la estructura

Ejecutar por separado en CMD:

if exist "D:\EXP_GIT\client\package.json" (echo CLIENTE_OK) else (echo CLIENTE_FALTA)

if exist "D:\EXP_GIT\server\package.json" (echo SERVIDOR_OK) else (echo SERVIDOR_FALTA)

Resultados esperados: CLIENTE_OK y SERVIDOR_OK. No combinar las validaciones con &, porque CMD puede asociar el segundo comando al bloque else.

3.2.2 Comprobar Node y npm

where.exe node
where.exe npm
node --version
npm --version

La primera coincidencia debe provenir de D:\node\node-v24. Versiones validadas:

v24.15.0
11.12.1

3.2.3 Instalar el servidor

cd /d "D:\EXP_GIT\server"
npm ci

3.2.4 Instalar el cliente

cd /d "D:\EXP_GIT\client"
npm ci

3.2.5 Instalar las dependencias de los widgets

Los widgets de Hidrograma utilizan tres módulos que no forman parte de la instalación base:

cd /d "D:\EXP_GIT\client"
npm install plotly.js-dist-min proj4 xlsx

npm list plotly.js-dist-min proj4 xlsx --depth=0

La validación debe mostrar los tres paquetes instalados sin errores.

Si node y npm apuntan a instalaciones incompatibles, la exportación puede fallar. Corregir el PATH antes de continuar. No ejecutar npm audit fix ni npm audit fix --force, porque pueden alterar las versiones fijadas por Esri.

4. Vincular los widgets directamente con Git

Detener el cliente de Experience Builder antes de crear las uniones. Revisar primero los widgets existentes:

dir /b /ad "D:\EXP_GIT\client\your-extensions\widgets"

En una instalación nueva debería aparecer únicamente simple.

4.1 Crear la unión del widget original

mklink /J "D:\EXP_GIT\client\your-extensions\widgets\hidrograma-interactivo" "D:\EXP_GIT\GIS_QB\widgets\hidrograma-interactivo"

type "D:\EXP_GIT\client\your-extensions\widgets\hidrograma-interactivo\manifest.json"

El manifest debe declarar name: hidrograma-interactivo y label: Hidrograma Interactivo.

4.2 Crear la unión del widget V2

mklink /J "D:\EXP_GIT\client\your-extensions\widgets\hidrogramaV2" "D:\EXP_GIT\GIS_QB\widgets\hidrograma-interactivoV2"

type "D:\EXP_GIT\client\your-extensions\widgets\hidrogramaV2\manifest.json"

El manifest debe declarar name: hidrogramaV2, label: Hidrograma V2 y la dependencia jimu-arcgis.

El mapeo V2 es intencional: la carpeta real del repositorio es hidrograma-interactivoV2, pero la unión, el manifest y la Experience usan hidrogramaV2. Al editar desde cualquiera de las dos rutas se modifica el mismo archivo versionado.

4.3 Crear la unión del widget Perfil de elevación

mklink /J "D:\EXP_GIT\client\your-extensions\widgets\perfil-elevacion" "D:\EXP_GIT\GIS_QB\widgets\perfil-elevacion"

type "D:\EXP_GIT\client\your-extensions\widgets\perfil-elevacion\manifest.json"

El manifest debe declarar name: perfil-elevacion, label: Perfil de elevacion, exbVersion: 1.20.0 y la dependencia jimu-arcgis.

4.4 Crear la unión del selector de imágenes drone

mklink /J "D:\EXP_GIT\client\your-extensions\widgets\selector-imagenes-drone" "D:\EXP_GIT\GIS_QB\widgets\selector-imagenes-drone"

type "D:\EXP_GIT\client\your-extensions\widgets\selector-imagenes-drone\manifest.json"

El manifest debe declarar name: selector-imagenes-drone, label: Selector de imágenes drone, exbVersion: 1.20.0 y la dependencia jimu-arcgis.

4.5 Compartir las dependencias del cliente

Webpack resuelve las uniones usando la ruta física dentro de GIS_QB. Crear una unión adicional para que encuentre el node_modules del cliente:

if exist "D:\EXP_GIT\GIS_QB\node_modules" (echo EXISTE) else (echo NO_EXISTE)

mklink /J "D:\EXP_GIT\GIS_QB\node_modules" "D:\EXP_GIT\client\node_modules"

Crear la unión únicamente cuando la comprobación devuelva NO_EXISTE.

cd /d D:\EXP_GIT\GIS_QB
git status --short

node_modules no debe aparecer en Git. Está ignorado y nunca debe agregarse al repositorio.

4.6 Confirmar los widgets vinculados

dir /b /ad "D:\EXP_GIT\client\your-extensions\widgets"

Resultado esperado, sin importar el orden:

hidrograma-interactivo
hidrogramaV2
perfil-elevacion
selector-imagenes-drone
simple
Las uniones de directorio mklink /J normalmente no requieren permisos de administrador. Revisar el exbVersion de cada manifest y usar la versión de Experience Builder acordada por el equipo.

5. Importar las Experiences

Los paquetes editables ya están versionados en Git y deben importarse sin abrirlos, extraerlos ni volverlos a comprimir:

D:\EXP_GIT\GIS_QB\experiences\packages\hidrograma-interactivo.zip
D:\EXP_GIT\GIS_QB\experiences\packages\hidrograma-interactivoV2.zip
D:\EXP_GIT\GIS_QB\experiences\packages\demo-perfiles.zip

Luego:

  1. Iniciar server y client.
  2. Abrir https://localhost:3001/.
  3. Ingresar al mismo portal usado por el equipo.
  4. Elegir Experience → Import → Import from my computer.
  5. Importar directamente los tres ZIP de experiences/packages.
  6. Abrir y guardar las Experiences importadas.
No crear paquetes de importación con Compress-Archive y no comprimir manualmente experiences/*/app ni server/public/apps/<id>. Esos ZIP devuelven Invalid App y appVersion: null. Solo son válidos los ZIP originales de Download o los generados por app-download.js con zipApp.
Los IDs locales pueden cambiar. En una máquina pueden ser 0 y 1, y en otra 4 y 5. Nunca suponer el ID sin revisar server/public/apps.

6. Ejecutar, editar y probar

Terminal del servidor:

cd /d D:\EXP_GIT\server
npm start

Terminal del cliente:

cd /d D:\EXP_GIT\client
npm start

Editar los widgets en:

D:\EXP_GIT\client\your-extensions\widgets\hidrograma-interactivo
D:\EXP_GIT\client\your-extensions\widgets\hidrogramaV2
D:\EXP_GIT\client\your-extensions\widgets\perfil-elevacion
D:\EXP_GIT\client\your-extensions\widgets\selector-imagenes-drone

Antes de exportar:

  • La Experience abre sin errores.
  • El widget muestra el cambio esperado.
  • Filtros, mapas y exportaciones funcionan.
  • No se incluyeron widgets ni recursos ajenos a la Experience que se entregará.
  • La Experience fue guardada en Builder.

7. Exportar y sincronizar

Primero guardar los cambios de las Experiences en la interfaz. Después identificar sus IDs locales:

dir /b /ad "D:\EXP_GIT\server\public\apps"
      
Revisar el info.json de cada ID mostrado hasta encontrar el título correcto:

      
type "D:\EXP_GIT\server\public\apps\0\info.json"
type "D:\EXP_GIT\server\public\apps\1\info.json"

      
Los IDs son locales y pueden cambiar en cada equipo. En la instalación nueva validada, el ID 1 corresponde a Hidrograma Interactivo V2.


      
7.1 Generar un paquete con Client ID

      
El Client ID validado para las aplicaciones desplegadas de este proyecto es BtJfYNpED0l11nil. Es un identificador público, no una contraseña. El tercer argumento de zipApp es obligatorio en el flujo del equipo; si se omite, el build queda con "clientId": "" y cambia el inicio de sesión.

      
if not exist "D:\EXP_GIT\GIS_QB\experiences\packages" mkdir "D:\EXP_GIT\GIS_QB\experiences\packages"
cd /d D:\EXP_GIT

set NODE_ENV=production&& node -e "require('./server/src/middlewares/dev/apps/app-download.js').zipApp('1', 'D:/EXP_GIT/GIS_QB/experiences/packages/hidrograma-interactivoV2-new.zip', 'BtJfYNpED0l11nil')"


      

        zipApp no sobrescribe un archivo existente. Generar primero un nombre temporal como *-new.zip; reemplazar el ZIP oficial únicamente después de validarlo.
      


      
7.2 Extraer y validar antes de reemplazar

      
if exist "D:\EXP_GIT\_stage_hidrogramaV2" (echo EXISTE) else (echo NO_EXISTE)

powershell -NoProfile -Command "Expand-Archive -LiteralPath 'D:\EXP_GIT\GIS_QB\experiences\packages\hidrograma-interactivoV2-new.zip' -DestinationPath 'D:\EXP_GIT\_stage_hidrogramaV2'"

dir /b /ad "D:\EXP_GIT\_stage_hidrogramaV2\cdn"

      
Usar el número devuelto por el último comando para revisar el archivo, por ejemplo cdn\2\config.json:

      
findstr /I /C:"clientId" "D:\EXP_GIT\_stage_hidrogramaV2\cdn\2\config.json"
findstr /I /C:"cdn/2" "D:\EXP_GIT\_stage_hidrogramaV2\index.html"

      
Resultados esperados: "clientId": "BtJfYNpED0l11nil" y una referencia de index.html al mismo número de CDN.


      
7.3 Reemplazar paquete y build de producción

      
move /Y "D:\EXP_GIT\GIS_QB\experiences\packages\hidrograma-interactivoV2-new.zip" "D:\EXP_GIT\GIS_QB\experiences\packages\hidrograma-interactivoV2.zip"

robocopy "D:\EXP_GIT\_stage_hidrogramaV2" "D:\EXP_GIT\GIS_QB\experiences\hidrograma-interactivoV2\app" /MIR /R:2 /W:1

      
Probar el build por HTTP antes de eliminar la carpeta temporal. Los códigos de salida de robocopy entre 0 y 7 se consideran correctos.


      
7.4 Limpiar después de validar

      
rmdir /S /Q "D:\EXP_GIT\_stage_hidrogramaV2"

      
Para la Experience original, repetir el mismo procedimiento usando su ID local y las rutas hidrograma-interactivo.


      
No se requiere xcopy para sincronizar los widgets: las rutas de your-extensions/widgets apuntan directamente al clon mediante las uniones creadas en la sección 4.


      

        Este flujo fue validado en Experience Builder 1.20.0: ambos ZIP generados con zipApp se importaron correctamente en un ambiente nuevo.

8. Commit, revisión y push

8.1 Crear una rama

cd /d D:\EXP_GIT\GIS_QB
git switch main
git pull --ff-only
git switch -c feature/descripcion-corta

8.2 Revisar

git status --short
git diff --stat
git diff -- widgets

8.3 Preparar únicamente el alcance autorizado

Para entregar widgets y paquetes editables:

git add -- "widgets/hidrograma-interactivo" "widgets/hidrograma-interactivoV2" "widgets/perfil-elevacion"
git add -- "experiences/packages/hidrograma-interactivo.zip" "experiences/packages/hidrograma-interactivoV2.zip" "experiences/packages/demo-perfiles.zip"
git add -- "experiences/hidrograma-interactivo/app" "experiences/hidrograma-interactivoV2/app" "experiences/demo-perfiles/app"
git diff --cached --stat

8.4 Commit y push

git commit -m "Describe el cambio"
git push -u origin feature/descripcion-corta
git status -sb

Abrir un Pull Request hacia main. Para trabajo colaborativo, evitar pushes directos a main.

9. Ver localmente la Experience de producción

No abrir index.html mediante file://. Servir la carpeta con HTTP:

cd /d "D:\EXP_GIT\GIS_QB\experiences\hidrograma-interactivoV2\app"
"D:\Env\arcgis-pro\python.exe" -m http.server 8080

Abrir http://localhost:8080/.

Experience Builder usa service workers. Si aparece una versión anterior, cerrar las pestañas, borrar los datos del sitio o probar en una ventana privada. Cada exportación puede incrementar la carpeta interna cdn/N; esto es normal y evita caché obsoleta.

10. Trabajo por roles

RolEntregaResponsabilidad
Developerwidgets/**Implementar y probar el código fuente del widget.
Analista GISexperiences/packages/*.zipIntegrar el widget, configurar la Experience, probar y exportar con zipApp.
RevisorPull RequestConfirmar que widget fuente y Experience compilada son consistentes.

Una rama puede recibir dos commits:

1. Improve Hidrograma V2 widget
2. Rebuild Hidrograma V2 experience
El código nuevo del widget no modifica automáticamente un ZIP ya versionado. Después de guardar la Experience, alguien debe regenerar el paquete con zipApp. main debería recibir el widget y su paquete editable como una unidad coherente.

11. Problemas frecuentes

SíntomaAcción
El widget no aparece en Builder.Confirmar la carpeta y el manifest.json; reiniciar npm start del cliente.
Module not found busca dependencias dentro de GIS_QB.Confirmar la instalación de plotly.js-dist-min, proj4 y xlsx, y crear la unión GIS_QB\node_modules hacia client\node_modules.
npm informa una versión distinta de Node.Ejecutar where node y where npm; corregir el PATH.
La Experience sigue mostrando el texto anterior.Guardar, recompilar, exportar nuevamente y limpiar la caché/service worker.
La importación devuelve Invalid App y appVersion: null.No recomprimir carpetas manualmente. Importar el ZIP original de Download o regenerarlo con zipApp.
El inicio de sesión del build descargado se comporta diferente.Revisar cdn/N/config.json. Si clientId está vacío, regenerar con el tercer argumento de zipApp: BtJfYNpED0l11nil.
La importación falla por versión o widgets.Verificar la misma versión de Experience Builder, el mismo portal y versiones compatibles de los widgets.
Git muestra muchos renombrados cdn/6 → cdn/8.Es esperado cuando cambia el número de build. Revisar que index.html apunte al nuevo directorio.
La Experience contiene perfiles.No publicar. Corregir la Experience editable y exportarla nuevamente.

12. Lista final antes del Pull Request

  • La rama parte de la última versión de main.
  • Los widgets fuente contienen los cambios.
  • Las Experiences fueron guardadas y sus paquetes se regeneraron con zipApp.
  • El texto o función nueva existe en el bundle compilado.
  • No hay secretos ni archivos temporales.
  • No hay widgets de perfiles ni recursos de otros clientes.
  • La Experience de producción abre mediante HTTP.
  • El Pull Request explica el cambio y las pruebas realizadas.
