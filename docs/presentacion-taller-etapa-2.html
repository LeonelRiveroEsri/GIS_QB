Punto de partida: el chat ya conversa con el usuario visualmente, pero todavía no tiene contrato, servicio ni acciones GIS conectadas.
Resultado de hoy

Convertir una maqueta de chat en un componente integrable.

No buscamos cerrar toda la inteligencia del producto. Buscamos una primera conexión completa, segura, observable y fácil de extender.

1

Entender el widget

Identificar estado, eventos, configuración y punto de integración.

2

Definir el contrato

Separar la interfaz del proveedor de IA y de las operaciones GIS.

3

Ejecutar una acción

Transformar una respuesta controlada en zoom, filtro o selección.

4

Dejar evidencia

Probar, versionar y documentar el incremento sin secretos.

Criterio de éxito: el widget envía una pregunta, recibe una respuesta estructurada y puede ejecutar al menos una acción GIS validada.
Agenda

Dos bloques, un recorrido punta a punta.

Primero estabilizamos el contrato y la conexión; luego incorporamos contexto GIS, seguridad y pruebas.

Arquitectura objetivo

El widget conversa; el backend gobierna.

El navegador presenta la experiencia y entrega contexto. Un servicio intermedio protege credenciales, valida las respuestas y controla qué puede ejecutar la IA.

Frontend

Responsabilidad del widget

Capturar mensajes, mostrar estados, aportar contexto mínimo y ejecutar solo acciones tipadas.

Backend

Responsabilidad del servicio

Ocultar secretos, autenticar, limitar consumo, construir prompts y validar la salida.

GIS

Responsabilidad de ArcGIS

Resolver consultas y geometrías con la identidad y permisos del usuario o servicio autorizado.

Regla no negociable: API keys, secretos de Azure y credenciales de servicio nunca se almacenan en el código del widget ni en el paquete público de Experience Builder.
Contrato antes que proveedor

Una respuesta que la interfaz pueda entender y validar.

El contrato desacopla el widget de OpenAI, Azure OpenAI u otro motor. La UI consume una estructura propia del proyecto.

Request del widget
{ "message": "Muéstrame el sector Mina", "conversationId": "session-123", "context": { "experience": "GIS_QB", "mapId": "...", "selectedSector": null } }
Response del servicio
{ "answer": "Sector Mina localizado.", "action": { "type": "zoomToSector", "parameters": { "sector": "MINA" } }, "sources": [], "requestId": "req-456" }
El texto se muestra. La acción se valida. Solo después se ejecuta contra el mapa.
Laboratorio guiado

Conectar por capas para aislar los problemas.

Si conectamos UI, red, autenticación, IA y GIS al mismo tiempo, un error no indica dónde mirar. Esta secuencia mantiene el diagnóstico simple.

1 · InventarioManifest, config, runtime, setting y mapa asociado.
2 · EstadoMensaje, historial, loading, error y cancelación.
3 · Cliente APIUna función responsable de HTTP y timeout.
4 · MockRespuesta estable con acción simulada.
5 · EndpointURL configurable por ambiente.
6 · AcciónValidación y ejecución controlada en el mapa.
✓ReadyEntrada disponible y contexto preparado.
…LoadingEvita doble envío y permite cancelar.
!ErrorMensaje útil, requestId y opción de reintento.
↻SuccessRespuesta, fuentes y acción aplicada.
Acciones GIS

Comenzar pequeño y explícito.

La IA no recibe acceso abierto al mapa. Devuelve una intención dentro de un catálogo limitado que el widget sabe verificar.

AcciónParámetrosValidaciónResultado esperado
zoomToSectorsectorExiste en la capa AOIZoom y flash del polígono
filterLayerlayerId, field, valueCapa y campo permitidosFiltro reversible y visible
selectFeaturelayerId, objectIdEntidad accesibleSelección y popup profesional
summarizeSelectioncampos, estadísticasSolo atributos autorizadosResumen con fuente y alcance

Confirmar acciones sensibles

Una acción con impacto debe pedir confirmación; consultar o navegar puede ser inmediata.

Mostrar el alcance

El usuario debe saber qué capa, filtro o selección utilizó la respuesta.

Poder deshacer

Filtros, gráficos temporales y selecciones deben limpiarse de forma predecible.

Seguridad y ambientes

Identidad, secretos y permisos desde el primer endpoint.

El demo puede usar un mock local. Una conexión real requiere definir quién llama, con qué permisos y dónde quedan las credenciales.

Guardrails mínimos

✓Sin secretos en React ni config públicaLas claves viven en variables protegidas del backend.
✓HTTPS y autenticaciónEntra ID/API protegida según el ambiente del cliente.
✓Lista blanca de acciones y capasNo se ejecuta código ni consultas arbitrarias.
✓Validación de esquemaLa respuesta del modelo se considera entrada no confiable.
✓Trazabilidad sin datos sensiblesrequestId, tiempos, resultado y error sanitizado.

Definition of Done

Probar más que la respuesta feliz.

La calidad del chat está tanto en cómo falla como en lo que responde.

A

Contrato

Request válido, respuesta válida, acción ausente, acción desconocida y JSON incompleto.

B

Red

Timeout, servidor caído, CORS, 401/403, cancelación y reintento sin duplicar mensajes.

C

GIS

Mapa no configurado, capa ausente, sector inexistente, entidad sin geometría y permisos insuficientes.

D

UX

Enter para enviar, foco, scroll, loading, historial, mensajes largos y diseño responsivo.

E

Seguridad

Sin secretos en bundle, parámetros validados, contenido escapado y logs sanitizados.

F

Entrega

Compila, funciona en localhost, commit acotado, revisión en testing y documentación actualizada.

Cierre del día

Un incremento pequeño, pero completo.

El chat deja de ser una caja visual y se convierte en una interfaz gobernada para el GIS.
